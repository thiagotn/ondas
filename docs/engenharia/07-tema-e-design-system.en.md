Ondas has nine themes, and each one defines **four things**: the background colour, the text colour,
the accent colour and the terminal's eight ANSI colours. Nothing else. There is no grey palette, no
border tone, no surface colour.

All of that is derived at runtime — 41 CSS variables per theme, generated by `color-mix` in the
oklab space. This document is about that generation, about the two traps it created, and about why
the whole project has a single `@media`.

## The problem: nine hand-written palettes are nine palettes to get wrong

The aesthetic is a terminal emulator's, and the themes are the real colour schemes from that world:
Catppuccin Mocha, TokyoNight, Dracula, Gruvbox, Nord, Rosé Pine, Solarized Dark, GitHub Light and
Nocturne (`packages/core/src/themes.ts:7-26`).

The interface needs far more than four colours: selected-row background, divider border, secondary
text, disabled text, panel background, shadow. Writing those twelve or twenty colours by hand for
each of the nine themes is 180 values — and, more seriously, 180 chances for one theme to end up
with worse contrast than the others without anyone noticing.

## The decision: two ramps and one mixing function

`packages/core/src/theme/tokens.ts` holds two derivation tables:

```
NEUTRAL: 9 stops, from pure text down to nearly the background   (100 → 9%)
ACCENT:  9 stops that switch targets halfway
```

The accent ramp is the clever part (`packages/core/src/theme/tokens.ts:13-16`): stops 100 through
400 mix the accent with the **text colour**, 500 is the pure accent, and 600 through 900 mix with
the **background**. A single ramp covers both "accent lighter than normal" and "accent faded until
it is nearly background", in any of the nine themes — including the light one, because the mix
always heads toward that theme's `fg` or `bg`, not toward white or black.

`themeCssVars(theme, opacity)` (`packages/core/src/theme/tokens.ts:34`) emits 41 tokens: 15 fixed, 9
neutral, 9 accent and 8 ANSI. And the implementation detail that matters: the values are
**unresolved `color-mix(in oklab, …)` strings**. JavaScript computes no colour at all; it assembles
expressions and hands them to CSS.

Why oklab and not sRGB: mixing in sRGB passes through muddy tones on the way (the classic greenish
grey between blue and yellow) and has uneven perceptual lightness. In oklab, 50% between two colours
looks like 50%. For a nine-stop ramp that needs even visual spacing across nine different themes,
that is the difference between deriving and hand-tuning each theme.

## The transparency trap

The layout handoff asked for background transparency with blur, in the style of Ghostty's
`background-opacity`. The naive implementation would apply alpha to everything. The result would be
text and borders losing contrast over the wallpaper.

The rule the code adopted (`packages/core/src/theme/tokens.ts:25-33`): **only two tokens become
translucent** — `--color-bg-a` and `--color-surface-a`. The neutral and accent ramps stay opaque,
because they are derived from the **solid** background — so text and borders keep the contrast they
had, regardless of what is underneath.

And alpha is applied in **sRGB**, not oklab (`cssAlpha`, `packages/core/src/theme/tokens.ts:23`).
Mixing with `transparent` in oklab produces a different result from what you expect in most
browsers; for plain alpha, sRGB is the right space.

The second trap is more serious, and the handoff named it before implementation: **no
`backdrop-filter` on the root**. A `backdrop-filter` creates a containing block, and that would
break every `position: fixed` overlay in the app — the full player, the access notice, the theme
picker and the splash. The solution is for blur to live in the wallpaper layer, with `filter`
(`packages/web/src/components/Wallpaper.tsx:43-46`), which creates no containing block.

The wallpaper is only rendered when `opacity < 1` and an image is chosen — at full opacity, zero
cost.

## Where `color-mix` does not serve

Three consumers need a **concrete** colour, in hexadecimal, and do not understand `color-mix()`: the
`theme-color` meta tag, the PWA manifest and phase 2's native theme provider
(`packages/core/src/theme/tokens.ts:61-64`).

That is why `packages/core/src/theme/oklab.ts` exists: 69 lines implementing the sRGB → linear →
oklab conversion and back, with Björn Ottosson's matrices, so that `mixOklab(a, pct, b)` produces
the **same value** the browser would produce with `color-mix(in oklab, …)`.

It is deliberate duplication of a function CSS already has. The alternative would be pinning a
hexadecimal per theme for `theme-color`, which would drift from what the screen shows the day
someone changed a ramp stop.

## The theme is applied before first paint

Switching theme after the screen's first paint is a white flash. To avoid it, there is an inline
script in `packages/web/index.html:41-74` that replicates the nine-theme table — only `bg`, `fg` and
`accent` — and applies four tokens before anything renders. Then a React effect applies the full set
(`packages/web/src/App.tsx:25-30`).

That is why the theme lives in `localStorage` and not IndexedDB
(`packages/web/src/theme/applyTheme.ts:25-28`): the script needs a **synchronous** read, and
IndexedDB is asynchronous. It is the same app using both stores for opposite reasons — this one
because it is synchronous, the wallpaper's because a 1 MB data URL does not fit `localStorage`'s
quota.

Duplicating the theme table in the HTML is an acknowledged cost. It covers three of the four fields,
and drifting from it means a flash of the wrong colour at boot — visible, but not broken.

One signature detail worth copying: `applyTheme(id, opacity)` takes opacity as a **required**
parameter (`packages/web/src/theme/applyTheme.ts:10-13`). The comment says why: forgetting it in any
call would silently return the app to opaque. *"O compilador cobra."* — the compiler charges for it.
That is cheaper than a silent default.

## The project's only `@media`

There are three `@media` queries in the code. Two are `prefers-reduced-motion`. **One** is about
layout: `packages/web/src/components/overlay.module.css:311`, `max-width: 859px`.

All other responsiveness is in JavaScript, through a hook: `useWide()`
(`packages/web/src/hooks/useWide.ts:7`), with `(min-width: 860px)` — the same breakpoint. The
difference is what each mechanism controls:

- `useWide` switches **structure**: on narrow screens the list shows no artwork and no share button,
the tabs become icons, the player hides its shortcuts
(`packages/web/src/components/TrackList.tsx:36-38`).
- The `@media` exists because there is a **height** calculation JavaScript would not solve better.

And the calculation is interesting. On a phone, the full player has to fit on screen **without
scrolling** — scrolling to reach the play button means losing the player. But the required height
cannot be pinned in pixels: the title takes one to three lines, and the buffer block may or may not
have a download button (`packages/web/src/components/overlay.module.css:300-310`).

The solution is inverting who yields: the panel gets a height ceiling and **the artwork takes
whatever is left** (`flex: 1 1 auto; min-height: 120px`). The product reasoning is direct — a
smaller button is useless, a smaller cover is not. Below ~570 px of height the artwork hits its 120
px floor and the screen starts scrolling again, which is the honest behaviour.

## Bands and content

On desktop, the background and borders of the tab bar, the footer and the toast run edge to edge,
but the content aligns to a 1,080 px column. The pattern is `.band` at full width and `.inner` with
a `max-width` and `margin: 0 auto`.

The consequence that justifies the pattern: **the scrollbar stays at the screen edge, not at the
column's.** Centring the whole column, scrollbar included, looks right in a mockup and wrong in use.

`--content-max: 1080px` (`packages/web/src/styles/global.css:6-15`) is the project's only token that
is **not** derived from a theme.

## How the CSS consumes the tokens

A one-way flow: `themeCssVars()` in the domain → `applyTheme()` → `setProperty` on the root
(`packages/web/src/theme/applyTheme.ts:17-19`). The ten CSS Modules only **consume** `var(--…)`: 243
references across 28 distinct names, and **no module declares a colour of its own**.

Two exceptions, both justifiable: the logo component injects an animation-speed variable inline
(`packages/web/src/components/CassetteLogo.tsx:49`), and the wallpaper passes `backgroundImage` and
`filter` inline, because both depend on runtime data.

There are three `@keyframes` in the entire project. The comment at
`packages/web/src/styles/global.css:116` says what that means in practice: *"O cursor é o único
movimento da interface."* — the cursor is the interface's only motion.

## What was rejected

| Option | Why not |
|---|---|
| Nine complete hand-written palettes | 180 values, and one theme with worse contrast without anyone noticing |
| Deriving by mixing in sRGB | Muddy tones mid-ramp and uneven perceptual lightness |
| Tailwind or a component library | Does not generate the derived ramps, and the theme switches at runtime |
| Alpha on every ramp | Text and borders would lose contrast over the wallpaper |
| `backdrop-filter` on the root | Creates a containing block and breaks every `position: fixed` overlay |
| A fixed hexadecimal per theme for `theme-color` | Would drift from the screen the day a ramp stop changed |
| The theme in IndexedDB | The pre-first-paint script needs a synchronous read |
| `@media` for all responsiveness | What changes on narrow screens is component structure, not only style |
| Pinning the full player's height in pixels | The title takes one to three lines and the buffer block is variable |

## What it cost

**The theme table exists in two places.** The HTML's inline script replicates three of the four
fields across nine themes. Drifting means a flash of the wrong colour at boot.

**`color-mix(in oklab)` reimplemented in JavaScript.** Sixty-nine lines duplicating what the browser
already does, for the three consumers that need hexadecimal.

**Two responsiveness mechanisms.**`useWide` and one `@media`, at the same breakpoint, and you have
to know which to use: structure in the hook, height in the CSS. The comments point at each other,
which helps and does not remove the cost.

**Every colour is derived, so a theme cannot have an exception.** If one of the nine needed a
lighter border than the ramp produces, there would be nowhere to put it without breaking the model.
So far none has.

## In an interview

**"How do you build a design system with nine themes?"** By defining the minimum per theme and
deriving the rest. Each theme has four things: background, text, accent and the eight ANSI colours.
The other 41 variables come from two nine-stop ramps, generated with `color-mix(in oklab)`. Writing
the palettes by hand would be 180 values and nine chances for one theme to have worse contrast
without anyone noticing.

**"Why oklab?"** Because mixing in sRGB passes through muddy tones and has uneven perceptual
lightness. In oklab, 50% between two colours looks like 50%. With nine themes and a ramp that needs
even visual spacing in all of them, that is the difference between deriving and hand-tuning.

**"How did you do background transparency without losing contrast?"** By making only two tokens
translucent: the background and the surface. The text and accent ramps stay opaque, because they are
derived from the solid background — so contrast does not depend on what is underneath. And blur
lives in the wallpaper layer with `filter`, never `backdrop-filter` on the root, which would create
a containing block and break every `fixed` overlay.

**"How do you avoid the wrong-theme flash on load?"** An inline script in the HTML applies the main
tokens before first paint. That is why the theme lives in `localStorage` and not IndexedDB: I need a
synchronous read. The cost is the theme table being duplicated in the HTML, and I accept it because
the alternative is a visible flash.

**"How many breakpoints do you have?"** One, used two ways. A `matchMedia` hook at 860 px decides
**structure** — on narrow screens the list shows no artwork, the tabs become icons. And there is
exactly one `@media` in the project, at the same breakpoint, for a height calculation: the full
player has to fit without scrolling on a phone, and the required height is variable because the
title takes one to three lines. The solution was giving the panel a ceiling and letting the artwork
yield — a smaller button is useless, a smaller cover is not.
