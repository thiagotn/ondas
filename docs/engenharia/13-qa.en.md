The question I now ask of every test I write in this project is:

> If I undo the fix this test exists to guard, does it fail?

Four times the answer was **no**. In all four cases the test looked good, covered the right line and
would have passed any code review. This document is about those four times, and about the structure
of the three suites around them.

## The three suites

| Suite | Count | Environment | Against what |
|---|---|---|---|
| Vitest, in the domain | **220** across 16 files | Plain Node, no jsdom | functions and stores in `packages/core` |
| Go | **123** across 16 files | A real Postgres | the API, the worker, ingestion, storage |
| Playwright | **37** × 2 viewports = 74 | Chromium | the PWA's **production build** |

Two structural choices decide each suite's character.

**The domain is tested without a DOM**, and not out of discipline: `packages/core` 's `tsconfig` has
no DOM library, so `document` and `window` are compile errors there. The consequence for tests is
that there is no jsdom to configure and no render to await — 220 tests run in 405 ms. The playback
queue, permission rules, link codec, waveform codec and the stores' transitions are all pure
functions or vanilla stores, testable by direct call.

**The web package has no unit tests at all.** Zero Vitest in `packages/web`. Its coverage is
end-to-end, and that is a choice: the bugs that code produces are about layout, focus, gestures and
the Service Worker — things a component test with a simulated DOM cannot see.

## The e2e suite runs against the production build

`packages/web/playwright.config.ts:13-18`: `command: 'pnpm build && pnpm preview'`. The development
server is never tested.

That costs build time on every run and pays off in two classes of bug that **only exist in
production**:

- **The Service Worker.** It is disabled in development. The `/api/` exclusion in the
single-page-app fallback ([document 06](06-pwa-e-offline.en.md)) is a bug that only appears with the
SW active.
- **Whatever is filtered at render time.** Development shortcuts are removed by
`import.meta.env.DEV`, which is a **runtime** filter, not a build-time one. I checked: the
network-simulation shortcut's string **is** in the production bundle. What the e2e suite proves is
that it is not **displayed** — and that distinction is only verifiable against the build.

The two viewports are `1280×800` and a Pixel 5 (`packages/web/playwright.config.ts:9-12`). Every
test runs in both, which is double the runs and catches the class of bug that appeared most in this
project: whatever fits on desktop and not on a phone.

## Tests that measure geometry

The e2e suite's dominant pattern is not checking for an element's presence — it is **measuring**. A
few test names:

```
packages/web/tests/smoke.spec.ts:584  o player cabe na tela sem rolar, e a capa continua quadrada
packages/web/tests/smoke.spec.ts:839  status line na mesma linha de base
packages/web/tests/smoke.spec.ts:886  abas: rótulo no largo, só ícone no estreito
packages/web/tests/smoke.spec.ts:961  forma de onda desenha o áudio conhecido e barra lisa quando não
```

The tabs one measures seven letters on wide screens and zero on narrow, and requires a **single
`top`** across the seven buttons — with the previous layout the measurement gives two rows. The
player one measures whether the total height fits the viewport and whether the artwork stayed
square.

The reason to measure is that the bugs in this codebase are visual. A test asserting "the button
exists" passes with the button off screen. And the reason I trust that style is a concrete case: a
phantom spacer in the narrow layout **did not appear in any test — it appeared in Playwright's
screenshot**. The test that covers it today was written after I saw the image.

## One Postgres schema per test

The 123 Go tests include a queue with `SKIP LOCKED`, a partial unique index and per-user scoping.
`api/internal/dbtest/dbtest.go:1-6` explains why they use a real database:

> as partes mais fáceis de errar do acervo […] só se provam contra um banco real; com um repositório
> de mentira o teste passaria descrevendo o que eu acho que o SQL faz.

*(…with a fake repository the test would pass describing what I think the SQL does.)*

Isolation is **one schema per test** (`api/internal/dbtest/dbtest.go:54`), not `TRUNCATE` between
tests. The reason is at `api/internal/dbtest/dbtest.go:50-53`:

> porque o `go test ./...` roda os pacotes EM PARALELO — com um schema só, um pacote apagava as
> linhas do outro e a suíte passava sozinha e falhava em conjunto.

"Passed alone and failed together" is the most confusing symptom a suite can have, because it
invites you to blame the code's concurrency rather than the test's isolation.

The mechanism has three good details:

- The `search_path` is pinned in the pool's connection parameters
(`api/internal/dbtest/dbtest.go:80`), so it applies to **every** connection it opens, including ones
created later — no query has to qualify a table name.
- Cleanup uses a fresh pool with its own deadline, and a cleanup failure is a log line, never a test
failure.
- The schema name carries the test's name (`api/internal/dbtest/dbtest.go:109`), *"para que um
schema deixado para trás (processo morto no meio) diga de quem era"* — so a leftover schema says
whose it was.

And migrations run through the **same production migrator**, not a parallel schema file. A schema
file just for tests is the most reliable way to test a database that does not exist.

### The guard protecting the real database

`api/internal/dbtest/dbtest.go:40-43`: the test database's name **must end in `_test`**, and that is
a `t.Fatalf`, not a `t.Skip`. The reason: the tests issue `DROP SCHEMA`, and an environment variable
carelessly pointed at the real database would touch the real library.

That is the difference between a convention and a guard. The production database's name never
satisfies the condition.

### What is skipped on purpose

Of the 123 Go tests, **68 skip** when `TEST_DATABASE_URL` is unset, and one more when
`ONDAS_AUDIUS_AO_VIVO` is. That is more than half the suite.

The decision is deliberate in both cases: requiring Postgres to run `go test` locally would be an
entry barrier, and a test against a third party's live API should not sit on CI's critical path
(`api/internal/audius/aovivo_test.go:15`).

But "skipped" is a dangerous state, because a skipped gate is exactly the same colour as a green
one. That is why CI brings up a Postgres as a service container, and the workflow comment says what
that buys (`.github/workflows/build-image.yml:19-21`): without that service, the migration-race test
*"viveria pulado"* — would live skipped.

The rule that stuck: **every test that can skip needs one place where it cannot.**

## The four times the test did not complain

### 1. The flattened artwork, and the noise that exposed it

The most elegant case, and it is entirely in the test's comment
(`api/internal/ingest/midia_test.go:178-181`):

> Ruído, e não um padrão de barras: o alvo de bitrate do encoder só aperta quando a imagem tem
> detalhe que não comprime. Medido aqui: com `testsrc2` o padrão dá 45dB e passaria neste teste; com
> ruído dá 31dB.

The context: ffmpeg's mjpeg encoder, without `-q:v`, targets a **bitrate** of 200 kbps instead of a
quality level, and eats the detail in a photograph. The fix was `-q:v 2`. The test exists to guard
it, measuring PSNR against the same source encoded nearly losslessly.

The first version used `testsrc2` as the source image — colour bars. And it **passed without the
fix**, because flat bars compress so well that they fit inside the bitrate target without losing
anything. The test measured the right thing, with the right metric, and was useless.

With seeded noise, the default gives 31.9 dB and the test fires. The seed keeps the measurement
repeatable.

> **A test that does not fail when the defect returns is not a guard — it only looked like one.**

There is a second methodological detail in the same test
(`api/internal/ingest/midia_test.go:171-174`): the reference is the same source encoded with
`-q:v 1`, and **not** the original PNG. That way JPEG's chroma subsampling is present on both sides,
and what the measurement isolates is only quantisation — which is what the parameter controls.
Comparing against the PNG would measure two things added together.

### 2. The `Enter` that would cancel its own button

When cursor navigation arrived in the list (`j` / `k` and `Enter` to play), I nearly put `Enter`
into the generic shortcut map. In that map `preventDefault()` is unconditional — and on a focused
button or link that **cancels the element's own click**. The activation key would stop activating,
across the whole app.

I caught that by reading the code, not from a test. The test came afterwards, and its name is the
bug's statement: `packages/web/tests/smoke.spec.ts:1300` — *"enter num botão focado ativa o botão, e
não a linha marcada"*. I confirmed it by mutation: undoing the fix makes it fail.

It is the case that shows the method's limit — mutation verifies a test that exists; it does not
write the test that is missing.

### 3. The `scrollIntoView` that did not need to scroll

The `:12` command moves the cursor to track 12 and scrolls to it. The test asserted that row 12 was
visible after the command.

I removed the `scrollIntoView` to check. The test **passed**: in the 1280×800 viewport, all twelve
rows of the demo catalogue fit on screen, so the target was already visible before the command. The
test asserted a true fact that had nothing to do with the fix.

The repair: shrink the viewport to 320 px of height and assert that the last row is **not** on
screen before `:12` and is after. The test started measuring the change, not the final state.

### 4. The overlay guard that changed nothing

`j` and `k` must do nothing while an overlay is open — the list is not on screen, and moving an
invisible cursor would leave `Enter` playing something nobody saw.

I removed the guard. The test **passed**, because the cursor was on the last row, where `j` does not
move anyway. The guard made no difference in that specific state.

The repair: put the cursor on track 01 first, with `:01`.

Cases 3 and 4 have the same shape, and it is the most common one: **the test was in a state where
the fix is irrelevant.** A test's initial state matters as much as its assertion.

## The risk the stub declares about itself

The e2e suite intercepts the API with a stateful stub (`packages/web/tests/smoke.spec.ts:87`), and
its docstring owns the risk out loud (`packages/web/tests/smoke.spec.ts:75-85`):

> **stub e API podem divergir. O contrato de verdade é coberto pelos testes Go** (status e mensagem
> de cada rota); aqui o que se testa é a PWA reagindo a ele.

And it mimics the contract with **the same Portuguese messages**, because the screen displays them
raw. It is conscious duplication with the division of responsibility written down: the Go suite
guarantees the contract; the stub guarantees the interface's reaction.

Two details of the stub that are real test engineering:

**The WAV is assembled by hand, byte by byte** (`packages/web/tests/smoke.spec.ts:37-56`): RIFF
header, 8 kHz mono 16-bit PCM. It exists because the audio route has to return **playable** audio —
with invalid bytes, the element fires `error`, the controller skips the track (which is its correct
behaviour) and the test never sees the library track in the player. The test would fail for a reason
other than the one it investigates.

**The test waveform has known relief** (`packages/web/tests/smoke.spec.ts:18`): a hundred characters
of the minimum value followed by a hundred of near-minimum, anchored to the codec's real alphabet.
That lets the test assert that the drawing's first half is lower than its second — an assertion
about the drawing, not about the element's presence.

And `skipSplash` (`packages/web/tests/smoke.spec.ts:221-225`) tolerates not finding the skip button
— the splash closes itself at a 4.5 s ceiling — but **asserts** that it ended up hidden. Tolerating
the path's absence while requiring the outcome is the right way to handle a race in a test; a
`catch` with no assertion afterwards would be a test that does not test.

## What was rejected

| Option | Why not |
|---|---|
| A mutation testing tool | None is configured; the practice is manual and aimed at the specific fix each test guards |
| Unit tests for React components | That layer's bugs are layout, focus, gestures and the Service Worker — a simulated DOM cannot see them |
| e2e against the development server | The Service Worker is disabled there, and the `DEV` filter is runtime, not build-time |
| `TRUNCATE` between Go tests | `go test ./...` runs packages in parallel; one would delete another's rows |
| A dedicated schema file for tests | Would test a database that does not exist; the production migrator is the same one |
| A fake repository instead of Postgres | The test would pass describing what I **think** the SQL does |
| Requiring Postgres for local `go test` | An entry barrier; CI is the place where nothing skips |
| Measuring the memory peak in the download test | Noisy and garbage-collector dependent; "no large `Blob` was constructed" is deterministic |
| Asserting PLAY/PAUSE after playing | The browser's autoplay policy has already caused flakiness in this codebase |
| A single viewport for e2e | The most common bug here is whatever fits on desktop and not on a phone |

## What it cost

**Mutation is manual, so it depends on me remembering.** There is no tool, no report, no CI gate.
The four cases in this document were caught because I asked; the ones I did not ask about are still
there.

**The e2e suite is slow.** It builds the application before running, and there are 60 runs. That is
the price of testing the artefact that goes to production.

**More than half the Go suite skips by default.** Locally, a green `go test ./...` means less than
it looks. CI closes the gap, and anyone running only locally needs to know that.

**The API stub can drift from the real contract.** The risk is declared and mitigated by the Go
suite, not eliminated.

**Tests that measure geometry break on legitimate layout changes.** That is noise in exchange for
catching the class of bug that appears most here. Worth it, and not free.

## In an interview

**"How do you know your tests are good?"** By undoing the fix they exist to guard and seeing whether
they fail. I did that four times in this project and four times the test passed without the fix. The
best case: a test measuring PSNR to guard an ffmpeg quality parameter used colour bars as its source
image — and bars compress so well they fit inside the bad bitrate target without losing anything.
With seeded noise the measurement drops from 45 to 31 dB and the test fires. A test that does not
fail when the defect returns is not a guard; it only looked like one.

**"What is the most common shape of a useless test?"** Being in a state where the fix is irrelevant.
Two of my four cases were that: the auto-scroll test passed because all the rows already fit in the
1280×800 screen, and the shortcut-guard test passed because the cursor was on the last row, where
the key does not move anyway. The initial state matters as much as the assertion — and the repair
for both was fixing the state, not the assertion.

**"How do you isolate database integration tests?"** One Postgres schema per test, with
`search_path` pinned in the pool's connection parameters, and migrations running through the
**same** production migrator. Not `TRUNCATE`, because `go test ./...` runs packages in parallel and
one would delete another's rows — the symptom was "passes alone, fails together", which is the most
confusing one there is. And the test database's name has to end in `_test`, with a hard failure if
it does not, because the tests issue `DROP SCHEMA`.

**"More than half your Go tests skip. Isn't that a problem?"** It would be, if there were no place
where they do not skip. Requiring Postgres to run the suite locally is an entry barrier I do not
want, so they are optional there — and CI brings up a Postgres as a service container precisely so
the migration-race test does not live skipped. The rule I follow is: every test that can skip needs
one place where it cannot. A skipped gate is the same colour as a green gate.

**"Why do your end-to-end tests run against the production build?"** Because two classes of bug only
exist there. The Service Worker is disabled in development, and the exclusion that stops the SPA
fallback from returning HTML instead of the API's JSON can only be proven with it active. And the
development-feature filter happens at **runtime**, not build time — the string is still in the
bundle; what the test proves is that it is not displayed.

**"Do you test React components in isolation?"** No, and that is deliberate. Zero unit tests in the
web package. The bugs that code produces are layout, focus, gestures and the Service Worker, and a
simulated DOM sees none of the four. What I have are end-to-end tests that **measure geometry** —
whether the player fits on screen without scrolling, whether the tabs stay on a single row — in two
viewports. A phantom spacer I had in that layout appeared in no test; it appeared in Playwright's
screenshot.
